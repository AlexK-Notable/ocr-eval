# Independent design review — Opus agent (with upstream verification)

**Date:** 2026-08-01 · **Reviewer:** Claude Opus subagent
**Artifact:** `docs/superpowers/specs/2026-08-01-ocr-eval-pipeline-design.md`
**Method note:** this reviewer verified the spec's factual claims against the live upstream artifacts rather than accepting them. Everything marked "measured" was computed from `qa_bank.json` (HF `Extend-AI/RealDoc-Bench`, revision `906170ab201d7b8238a32a9115fc66b4b72e0710`) and the harness at GitHub `extend-hq/realdoc-bench` HEAD `fb26a68764`.

---

## 1. The headline metric does not measure checkboxes

**Problem.** Stage 1's primary output column is "checkbox accuracy (strict per-question)" over the 429-question checkbox bucket. I measured the bucket's composition: 429 questions / 263 docs (spec's numbers confirmed), **1,117 gold fields, of which only 258 (23.1%) are boolean.** 731 are strings, 65 int, 33 null, 26 float, 4 list. Worse: **248 of the 429 checkbox-tagged questions contain zero boolean fields at all** — only 181 have ≥1 boolean, and only 120 are all-boolean. Questions are multi-field; a representative one (`finance_q4`) asks for one checkbox state *plus two policy numbers*.

**Why it matters.** Strict per-question accuracy on this bucket is ~77% determined by string and number extraction. The project exists to produce "the checkbox number that does not exist," and as specced it would publish a general-extraction number under a checkbox label. Every downstream ranking claim inherits the mislabel.

**Fix.** Define the primary metric as **per-field accuracy restricted to boolean-typed gold fields inside checkbox-tagged questions** (n=258 fields over 263 docs) — the type is available directly from `gold_dict` (`isinstance(v, bool)`). Report strict per-question over the bucket as a clearly separate general-extraction column. Name them so they cannot be conflated.

## 2. No trivial baselines, and the boolean class balance puts the floor at 64%

**Problem.** Measured gold boolean balance in the checkbox bucket: **165 True / 93 False. A constant "checked" predictor scores 64.0% per-field.** The spec's report has no majority-class row, no always-true/always-false row, and no no-image control.

**Why it matters.** `gate3-eval-spec.md` explicitly required "both polarities represented … or a model that answers 'checked' to everything scores well." The data does not have balanced polarities, so the guard must move into the report. Absent it, a 68% result reads as competence when it is +4 points over a constant. A no-image control (question text only, no page) is also near-free and catches the classic VQA language-prior confound — form questions like "Is the applicant a US citizen?" are partly guessable.

**Fix.** Add three zero-cost synthetic rows to every report: always-true, always-false, majority-class; print the gold class balance next to the table. Add a no-image control row for at least one model. Refuse to rank any model that does not beat the constant predictor by more than its CI.

## 3. The spec mischaracterizes the scorer it plans to vendor

**Problem.** The spec says: "Metric: normalize-then-exact" and proposes to vendor "normalization rules and `capability_buckets.yaml` … as data." The actual upstream scorer (`realdoc_bench/evaluate/score.py`, 450 lines) is:

> parser markdown → **one `gemini-3-flash-preview` call per (question, parser)** with a fixed 26-line `SYSTEM_PROMPT` and a typed JSON template → `deep_equal`, **with `fuzzy_equal` (rapidfuzz ratio ≥ 92, only when both sides have ≥5 words) on plain `<string>` fields**.

The README states it plainly: *"an LLM extractor (Gemini 3 Flash) is asked to answer the question from the parser's markdown alone."*

**Why it matters.** Three consequences the spec does not account for. (a) It is not exact match — 731 of the 1,117 checkbox-bucket fields are strings and get fuzzy credit. (b) The typed template is generated by `build_template` / `jsonify.py` (`_placeholder_to_type_hint`, `widen_types_from_gold`, `render_template`) — machinery the spec never mentions; vendoring "normalization rules" leaves it out and the vendored normalizer will not run. (c) **Every published RealDocBench number is a two-stage transcribe-then-extract pipeline by construction.** There is no upstream analogue of the spec's `vlm-chat` shape, so no `vlm-chat` row is comparable to the published leaderboard.

**Fix.** Vendor `score.py` + `jsonify.py` + `SYSTEM_PROMPT` + `FUZZ_THRESHOLD`/`FUZZ_MIN_WORDS` as one unit at a pinned commit. State explicitly whether the pinned extractor is `gemini-3-flash-preview` (comparable to published numbers, but a closed paid Google dependency) or a substitute (not comparable) — and record which on every row. Note also that upstream's own `gemini_3_5_flash` parser is judged by a same-family extractor; any transcriber+extractor pairing from the same family is not neutral and should be flagged.

## 4. Stage 1's "lenient" contract discards the benchmark's own typed contract — and breaks the null measurement

**Problem.** Every bank item ships a `response_format`, e.g. `"Return exactly: question_4_checkbox_marked=<boolean>; right_column_wc_policy_number=<text>"` and, for blank-field items, `"Return exactly: state=<text|null>"`. Upstream converts this into the typed template that tells the model which fields are boolean and which may be null. The spec's Stage 1 condition is `output_contract: lenient` — "request JSON in the prompt, parse tolerantly (fenced JSON, bare value, yes-no synonyms)" — which throws that away and substitutes a hand-rolled synonym mapping.

**Why it matters.** Two distinct damages. (a) Booleans stop being typed, so *your* yes/no synonym table decides polarity — the single most outcome-determining piece of undefined logic in the design, and where inversion bugs live. (b) Null-permitted fields no longer signal nullability, so the model is never told null is a legal answer. The blank-field hallucination rate then measures something stricter than and incomparable to upstream. The staging is inverted: the **schema** contract is the comparable baseline; **lenient** is the novel condition.

**Fix.** Make Stage 1 use the bank's `response_format` → typed template as the output contract. Move `lenient` to a Stage 2 axis value if it is still wanted. If lenient stays in Stage 1, the answer value domain (`true` / `false` / `null` / unanswerable) and the full synonym table must be written into the spec, versioned as data, and covered by golden fixtures per mapping — in particular the `false` (box present, unchecked) vs `null` (field blank) distinction, which is the crux of both the checkbox and the hallucination measurement and is currently undefined.

## 5. The blank-field bucket has 34 null golds, not 188

**Problem.** The spec states "blank-field bucket (122 questions, 188 null golds)". Measured: the `blank_field`-tagged set is **122 questions covering 270 fields, of which 34 are null.** The bank has 188 nulls total; **154 of them (82%) live outside the bucket.** Additionally, **40 questions belong to both the checkbox and blank-field buckets** — the spec never says whether buckets are disjoint.

**Why it matters.** An implementer computing the hallucination rate over the bucket gets n=34, roughly ±12 points at 95% — far too noisy to rank anyone, and nothing like the precision the spec's framing implies. The scientifically right denominator is all 188 null-gold fields, which requires running the **full 1,356-question bank**, not the ~511-question two-bucket subset Stage 1 scopes. That is a real cost and scope decision, currently made by accident.

**Fix.** Correct the number in the spec. Decide explicitly: either run the full bank (recommended — it also enables Finding 8's reproduction check) or accept n=34 and print the interval next to it. State bucket overlap and whether the 40 shared questions are counted in both columns.

## 6. No confidence intervals — the ranking will not be defensible

**Problem.** The report is point estimates only. RealDocBench's own paper publishes 95% **document-clustered** bootstrap CIs precisely because multiple questions share a document (429 questions over 263 docs — the clustering is severe). The published open-weight rows carry intervals of ±2.4 to ±4.0 points.

**Why it matters.** On 258 boolean fields clustered in 263 documents, differences under roughly 8 points are not resolvable. A markdown table with a confident ordering will be read as a ranking and cited as one. This is the exact failure the survey criticised in others.

**Fix.** Document-clustered bootstrap CIs on every accuracy number, and **paired** bootstrap for model-vs-model deltas (same questions, so paired intervals are much tighter than the difference of two marginals). Print "not separable" rather than an order when intervals overlap. The Stage 3 hard-case slice (measured: `filled_bubble` 16, `circled_choice` 7, `ambiguous_mark` 6, `crossed_out` 1) must stay qualitative, which the spec already says correctly.

## 7. `vlm-chat` and `transcriber` rows are put in one ranked table

**Problem.** A `vlm-chat` row measures one model. A `transcriber` row measures (transcriber ∘ pinned extractor). The spec's extractor-cancellation argument is valid *within* transcriber comparisons and silently invalid across shapes — yet the Stage 1 output is "one markdown report — rows are registry entries."

**Why it matters, specifically for checkboxes.** A transcript is a lossy intermediate for checkbox state: if the transcriber emits `☑ Yes ☐ No` the extractor can read it; if it emits `Yes No` the information is destroyed before scoring. So the transcriber's checkbox score is dominated by markdown-convention conformance — which is precisely the GLM-OCR "ParseBench 29.6 is format conformance, not reading ability" hypothesis the survey wants to test, here baked into the Stage 1 headline instead. Upstream already controls for this: its markdown prompt mandates *"Render checkboxes inline as ☒ (checked) or ☐ (unchecked), paired with their adjacent label on the same line"* and *"If the value is empty, emit `**<label>:** <blank>`"*. The spec never mentions a transcription output contract.

**Fix.** Vendor upstream's `_MARKDOWN_PROMPT` verbatim for prompted transcribers and record its hash. Add a **transcript-recall diagnostic**: does the transcript contain any checkbox glyph and the target field label at all — separating "read it wrong" from "never emitted it". Segregate the report into shape-labelled sections, with transcriber rows labelled `(transcriber + extractor <id>)`. Dedicated OCR endpoints that accept no prompt cannot be given this contract, which is an unavoidable asymmetry that must be stated rather than hidden.

## 8. Nothing validates the pipeline end-to-end against a known-good number

**Problem.** The golden-fixture self-test validates the **scorer**. It cannot catch a wrong DPI, a wrong prompt, a wrong template derivation, a wrong bucket filter, or a wrong page render — all of which shift every model equally and are therefore invisible in a relative ranking.

**Why it matters.** This is the systematic-error class, and it is the one that produces a confidently wrong published number.

**Fix.** Add to the Stage 1 definition of done: **reproduce a published RealDocBench system's per-field and per-question score within its CI.** Suitable targets are open-weight, vLLM-servable, and already in the candidate set: dots.ocr (2-stage) 70.6±3.6 / 61.4±3.5, olmOCR-2 79.5±2.6 / 67.9±3.0, PaddleOCR-VL 59.6±4.0 / 48.5±3.6. Note the reproduction target must come from the **paper**, not the README: the current README leaderboard has 10 rows and **no open-weight entries at all**, uses new naming (`Extend Parse 2.0`, `Extend Parse Light 1.0`), and has added Mistral OCR 4 at 88.8/81.3 — it has already drifted from the Table 3 the survey transcribed.

## 9. Bucket filtering is fail-open, and the vendored file documents the hazard itself

**Problem.** `capability_buckets.yaml` says verbatim in its header: *"Unknown tags are silently skipped — `n_qs` will read as 0 for that bucket."* The spec vendors this file as authoritative data with no cardinality assertion.

**Why it matters.** This is exactly the fail-open shape of standing lesson `lrn-ea833a5b`: a tag rename upstream yields an empty bucket, a clean exit, a green scorer self-test, and an empty or partial report that looks like a successful run.

Two related data problems, measured. (a) The tag vocabulary is dirty — ~140 distinct tags including duplicate spellings (`field extraction` 8 vs `field_extraction` 5; `table extraction` 4 / `table_extraction` 9 / `table-extraction` 2). (b) The Checkboxes bucket's three tags omit checkbox-relevant tags present in the bank: `checkbox_grid_alignment` 8, `four_way_checkbox_grid` 5, `n_a_vs_n_o` 5, `checkbox_parsing`/`checkbox_binding`/`checkbox_grid`/`checkbox_state_extraction` 1 each, plus the hard-case tags `filled_bubble` 16, `circled_choice` 7, `ambiguous_mark` 6, `crossed_out` 1. Blank-field similarly omits `null_handling` 2, `blank_recognition` 2, `empty_cell_recognition` 2, `empty_cell_handling` 2, `null_extraction` 2, `blank_vs_value_mixed` 9.

**Fix.** Hard preconditions, fail-closed, before any spend: checkbox bucket == 429 questions / 263 docs / **258 boolean fields**; `blank_field` == 122 questions / **34 null fields**; bank == 1,356 items / 3,742 fields / **188 nulls**. Add a non-blank render check (ink-coverage floor) per page. Then decide explicitly whether to use upstream buckets verbatim (comparability) or an extended checkbox tag set (coverage) — and if extended, report both.

## 10. The precision policy protects the wrong comparison

**Problem.** The rule flags *local-vs-hosted of the same weights at different precision*. The headline comparison is model-A vs model-B. Per the policy, the 0.9–3B OCR specialists run BF16 locally while the two top-ranked Tier A candidates (Qwen3-VL-8B, Qwen3.5-9B) run FP8. That is a precision confound **between the two groups being ranked**, and a footnote does not remove it.

Separately, `precision: bf16 (provider default)` on hosted rows is an assumption recorded as a fact. OpenRouter routes across providers with differing quantization and can switch between calls; the risk-table mitigation ("registry snapshot recorded per run") records an unknown.

**Fix.** For any model appearing in the headline table, run all its rows at one precision, or run both and publish the delta. Pin OpenRouter routing (`provider.order` + `allow_fallbacks: false`) and record the **provider actually returned in the response body**, not the configured one; treat unpinnable serving paths as a separate labelled tier. Pin and record the vLLM version in run metadata — kernel and quantization changes alter outputs.

## 11. The accuracy denominator is never defined

**Problem.** "Parse failures are not wrong answers … never folded into accuracy." Upstream does the same (`summarize()` filters on `r.ok`) but always prints `n_results` alongside. The spec's report columns list no denominator.

**Why it matters.** A model that fails 40% of cells and scores 90% on the rest ranks above one that always answers at 85%. For deployment, an unparseable answer is a failure. Two reasonable implementers will pick different denominators and produce incompatible tables.

**Fix.** Report both accuracy-over-answered and accuracy-over-all (errors counted wrong), print n per cell, and make accuracy-over-all the ranking key. Also resolve: a `refusal` on a null-gold field is arguably the *correct* answer, not an error — decide and document which.

## 12. Fixed DPI does not fix effective resolution, and 200 is not the upstream value

**Problem.** Upstream `_vision_base.py` sets `DEFAULT_DPI = 150` and rasterizes with **pymupdf** (`page.get_pixmap(matrix=Matrix(dpi/72, dpi/72))`). The spec picks 200 DPI via `pdftoppm`. More importantly, DPI does not fix pixel count when page sizes vary. Measured across a 16-doc stratified sample of the checkbox bucket: 612×792pt (letter), 841.92×595.32pt (A4 landscape), 768×1152pt, 636×799pt, 602×767pt, 592×758pt. At 200 DPI that spans **1700×2200 up to 2133×3200 (6.8 MP)** — a ~1.9× area spread, with the largest class concentrated in mortgage and supply_chain.

**Why it matters.** Hosted providers silently downscale above their own caps, differently per provider, so the "hidden condition" the spec correctly identifies is not actually pinned by recording DPI — and the downscaling penalty lands hardest on specific domains, producing a domain-correlated resolution confound. Checkbox marks are small; effective resolution is the dominant physical variable here.

**Fix.** Pin the **long edge in pixels**, not DPI. Record actual pixel dimensions and encoded byte size per row, plus provider-reported image token counts where exposed. If leaderboard comparability matters, match upstream exactly: 150 DPI, pymupdf.

## 13. Rebuilding an Apache-2.0 harness that already does most of Stage 1

**Problem.** The spec vendors only "normalization rules + bucket defs" and builds registry, cache, pricing/dry-run, runner, and report from scratch (~600–800 lines). Upstream already ships, under Apache-2.0: `shared/registry.py`, `shared/io/cache.py`, `shared/pricing/catalog.yaml` + `meter.py`, `evaluate/runs.py` (run layout), `evaluate/report.py` + `report_template.html`, `shared/reporting/{leaderboard,pareto,plots}.py`, parse-stage caching/retries/page-concurrency, and **parsers for `mistral_ocr`, `azure_di`, `aws_textract`, `reducto`, `llamaparse`, `extend`, plus a generic `cloud_vlm` VLM-as-parser** built on a page-fanout base class. Stage 1's DoD requires "≥1 hosted OCR endpoint" — already implemented upstream.

**Why it matters.** Rebuilding is not just cost; every divergence is a comparability break with the only published numbers on this instrument (Findings 3, 4, 7, 8, 12 are all instances of this).

**Fix.** Seriously evaluate fork-and-extend over rebuild. The genuinely new work is small: an OpenAI-compatible `vlm-chat` provider (a ~40-line subclass of `VisionParserBase`, mirroring `cloud_vlm.py`), a local-vLLM transcriber, the condition axes, boolean/null-restricted metrics, CIs, and baselines. Smaller YAGNI items regardless of that decision: the registry-level circuit breaker (bounded retries suffice for ~550 questions × ~6 models), bespoke pre-run pricing tables for a single-digit-dollar run (read realized cost from response usage instead), and automatic local/hosted scheduling by `base_url` when local server launch is manual anyway. Note also: upstream loads secrets from a `.env` file — if forking, that must be disabled or explicitly gitignored to honour the environment-only constraint.

## 14. Cache-key omissions, a Stage 2 collision, and no re-score path

**Problem, four parts.**
- The key omits the **rendered image content hash**. A renderer change, DPI-code change, or re-fetch silently reuses stale responses.
- It omits the **resolved provider and model version**. The claim "old results stay valid forever because keys never change meaning" is false for hosted models that update silently under a stable id.
- Stage 2's `schema` mechanism ("native structured output or prompt-enforced; mechanism actually used is recorded per row") is recorded outside the condition dict, so it is **not in the cache key**. A model that later gains native structured-output support collides with its old prompt-enforced entry. It is also a confounded contrast — two different treatments assigned non-randomly by model capability, which recording cannot fix.
- Scores are materialized into immutable JSONL rows with no re-score command. Upstream deliberately re-scores cached answers with current scoring code on every cache hit, so fixing a normalization bug costs nothing.

**Fix.** Add image content hash and a resolved-serving-identity hash to the key. Promote the schema mechanism to a distinct condition value (`schema_native` / `schema_prompted`) so it enters the key and cannot be pooled in the report. Add an `ocr-eval rescore` command recomputing parsed/normalized/score from stored raw responses. Make the transcriber cache **two-level** — transcript keyed on (image hash, transcriber, condition), extraction keyed on (transcript hash, question id, extractor) — otherwise the same page is transcribed once per question and per-call transcription variance leaks into per-question scores.

Related: Stage 2's K-sample axis sets "temperature per-registry". Agreement rate is monotone in temperature, so a cross-model agreement table with per-model temperatures is meaningless. Put temperature in the condition dict and use a common value for the cross-model table.

## 15. The registry records weights licence but not provider ToS — the constraint the survey said binds harder

**Problem.** `gate3-conclusion-ranking.md` PART 2 is headed "Provider ToS is the binding constraint, not the weights licence": Novita bars commercial endeavors, Z.ai bars finance/insurance/medical/legal, Fal bars exposing the API to end users, **Datalab's EULA §10(a) restricts Output to internal use**. The spec's registry schema has `licence:` (weights) and `provenance:` only — and it names "Marker/Surya on Replicate" as a `transcriber` exemplar without carrying the Datalab flag.

**Why it matters.** The user's fixed constraint is that candidates be usable in closed-source self-hosted commercial projects. Stage 3 correctly generates the CheckboxQA CC BY-NC stamp *in code* rather than relying on memory. The same discipline is absent for the far more numerous provider-ToS blockers, which is where the survey concluded the real eliminations happen.

**Fix.** Add `weights_licence`, `provider_tos_commercial: ok | blocked | conditional`, and `tos_note` to the registry entry; make the report stamp any row whose serving path is commercially blocked, generated not remembered. Also add the CC-BY-4.0 attribution line for RealDocBench to Stage 1 reports by the same mechanism.

## 16. Two pins are needed, not one — and one of them is not "plain HTTPS"

**Problem.** The spec says the loader "fetches PDFs + `qa_bank.json` over plain HTTPS (no auth), verifies checksums, pins the upstream commit" — singular. In reality there are two independently-versioned artifacts: the **data** is an HF dataset repo (`Extend-AI/RealDoc-Bench`, CC-BY-4.0, revision `906170ab201d7b8238a32a9115fc66b4b72e0710`, lastModified 2026-06-03; upstream fetches it via `huggingface_hub.snapshot_download`), and the **harness/bucket definitions/scorer** are GitHub (Apache-2.0, HEAD `fb26a68764`, 2026-07-30). They drift independently.

**Fix.** Record both, name the fields distinctly (`dataset_revision`, `harness_commit`), and put the current values in the spec so the implementer does not have to guess which "upstream commit" was meant.

## 17. Text-layer free rides across transcribers

**Problem.** Measured in the 16-doc sample: 14 documents have **zero** extractable text; 2 do (`finance_54` 1,039 chars, `finance_74` 514 chars). Pipeline transcribers that read the embedded PDF text layer when present — Marker and Docling do by default — get an error-free transcript on those documents while image-only models must OCR the raster.

**Fix.** Force raster-only input for all transcribers (render to PNG and feed the image, never the PDF), or record which path each document took and report that subset separately. The spec's `transcriber` contract says "receives page image(s)", which is right — but nothing enforces it for tools handed a PDF path.

## 18. `--dry-run` cannot see the scoring model's cost

**Problem.** `--dry-run` prices "cells × estimated tokens × registry pricing". If the extractor is an LLM — it is, upstream — then every (question × transcriber) cell incurs an additional extractor call that the estimate never sees. At 429 questions × N transcribers, that is a whole second cost centre, on a *different* provider (Google), requiring a key the spec never mentions.

**Fix.** Price the extractor leg explicitly; report transcription cost and extraction cost as separate columns; compute realized cost from response `usage` fields rather than a hand-maintained pricing table that goes stale. Also note in the report that `$/1k questions` and `median latency` are not comparable between local and hosted rows — currently they sit in one table implying comparability.

## 19. Risks the table omits

- **Benchmark contamination.** Dataset public since 2026-06-03; several candidates (Qwen3.5 line, GLM-OCR, PaddleOCR-VL-1.6) post-date it, and the source PDFs come from public government archives that may be in pretraining data regardless. Record model release date vs dataset date and flag.
- **Partial matrices rendered as complete.** The circuit breaker pauses a registry and the run exits nonzero, but nothing prevents the report from rendering a row assembled from a partial cell set. Assert per-row cell completeness; mark incomplete rows.
- **Non-determinism at temperature 0** on batched serving — undermines the reproducibility claim and complicates Stage 2 agreement interpretation.
- **No hard budget cap during a run** — only a pre-run estimate.
- **Local OOM, not just "doesn't fit".** vLLM's default `gpu_memory_utilization=0.9` on 16 GB, combined with dynamic-resolution vision tokenization on a 2133×3200 page, is a distinct failure mode from "model too large". The row "16 GB insufficient for a wanted local model" does not cover it.
- **Upstream drift on the comparison target** — the README leaderboard has already changed since the survey. Snapshot the target table alongside the pins.
- **Multi-page documents.** All 16 sampled docs are single-page, and the bank has **no page index** (item keys are exactly `capabilities, domain, gold_answer, gold_dict, question, question_id, response_format, source_file`). That de-risks page selection — but the design has no page-selection story at all, so the loader should assert `page_count == 1` and fail loudly if a multi-page document appears, rather than silently changing what the model sees.

## 20. Remaining underspecification an implementer would trip on

- **No frontier calibration anchor in Stage 1.** `gate3-eval-spec.md` asked for "one frontier baseline for calibration"; the DoD drops it. Without an anchor you cannot distinguish "small models are bad at checkboxes" from "this bucket is hard". Gemini 3.5 Flash is on the leaderboard at 89.3/82.2 *and* is upstream's `cloud_vlm` parser — it serves as anchor and reproduction target at trivial cost.
- **`transcriber` conflates shape with transport.** The spec defines `vlm-chat` as "OpenAI-compatible chat completions" and `transcriber` by output shape, but Stage 1 requires a hosted OCR endpoint, and those transports differ wildly (Replicate async polling; Mistral OCR's own document API; Azure DI's `operation-location` polling; Textract/Azure DI return structured field JSON rather than a transcript and need a markdown normalizer). "Never a third shape" survives only because upstream already wrote those adapters. State that `transcriber` is a Python Protocol `(images, condition) -> TranscriptResult` with per-provider adapters, and name the concrete Stage 1 adapter.
- **"PaddleOCR pipeline" is ambiguous** — the spec uses it for a Stage 2 classical transcriber while PaddleOCR-VL (a vLLM-served model) is a Stage 1 candidate. These are different systems with different scores; disambiguate the names.
- **Golden fixtures' provenance** is unstated — hand-written or drawn from the real bank (which would leak)?
- **Effort estimate** of 600–800 lines for Stage 1 looks low by roughly 2× once transport adapters, local vLLM bring-up, CIs, baselines, and tests are real — and the DoD includes standing up vLLM for a specialist, which is a session on its own.

---

**What is sound.** The core instincts are right and unusually disciplined: a condition dict present from commit one with cache keys that never change meaning; a fail-closed scorer self-test with a deliberate polarity-inversion fixture; error classes kept out of accuracy rather than silently folded in; one registry entry per (model, serving) pair so the same weights served two ways never merge; the precision policy's refusal to compare Q4-local against BF16-hosted; per-cell error isolation with fail-visible nonzero exit; `PIPESTATUS` discipline; the CheckboxQA licence stamp generated in code rather than remembered; the mixed-provenance `origin=None` caveat auto-printed; hard-case tags preserved from Stage 1 though unreported until Stage 3; and the explicit non-goals list. The staging itself is well-chosen — Stage 1 genuinely is the minimum that answers a real question, and Stage 3's HITL analysis correctly reuses Stage 2 rows at zero new API cost.
